### 09:34~09:44 LLM API 활용 방식과 에이전트에 대한 통제
- OpenAI뿐 아니라 Claude, Google(Gemini) 등 여러 LLM 플랫폼 API를 쓰면 기능을 쉽게 만들 수 있다는 이야기로 시작.
- 작업을 누가 결정하느냐가 핵심이라고 설명: **코드가 결정**, **에이전트가 결정**, **에이전트가 다른 에이전트에게 위임**하는 세 가지 방식.
- 에이전트는 스스로 판단·결정하므로 "위임"이며, 사람이 짠 코드는 결과를 추적·설명하기 쉽지만 에이전트끼리 위임하면 통제와 결과 예측이 매우 어려워진다.
- AI 기술이 매우 빠르게 발전하고 있으니 개발자도 그 흐름을 따라가야 한다.
- 학습 태도: 먼저 넓게 훑고, 필요한 부분이 생기면 AI를 활용해 깊이 파고드는 방식을 권장.

### 09:43~09:52 에이전트 프레임워크: LangChain과 LangGraph
- 오늘 다룰 프레임워크로 LangChain, LangGraph 등을 소개.
- LangChain은 앞 단계의 결과를 다음 단계가 받아 이어 가는 **일직선 체인** 구조.
- LangGraph는 LangChain 위에서 동작하며, 사람이 노드와 엣지를 만들고 연결하므로 어떤 흐름으로 처리되는지 정확히 알 수 있다.
- 에이전트를 운영하려면 파일 시스템, 서브에이전트, 스킬, 메모리 파일 같은 요소가 필요하다고 언급(세부 설명은 인식이 불분명).

### 09:52~09:58 "AI로 코드를 만들고, 일은 코드가 하게 하라"
- 매일 반복 실행되는 시스템을 매번 AI(에이전트)에 맡기면 결과가 조금씩 달라져 문제가 생긴다.
- 개발자의 일은 AI로 코드를 만들어 두고, 실제 운영은 LLM을 쓰지 않는 코드가 하도록 하는 것.
- AI로 금방 만들었다고 실력이 아니다. 전체 구조를 이해하고 코드를 모두 설명할 수 있어야 전문가다.
- 안전장치는 코드로 만들고, 위험한 부분은 계속 검증해야 한다.
- **문서화(documentation)가 가장 중요**: 문서가 있으면 나머지는 AI로 다시 재현할 수 있으므로, 작업 내용을 항상 기록하는 습관을 들일 것.

### 09:58~10:04 예시 워크플로: 매일 아침 보안 취약점 점검
- 출근하면 회사가 쓰는 소프트웨어 자산과 버전 목록(예: Apache)을 확인.
- NVD에서 어제 새로 등록된 관련 CVE를 조회하고, 함께 연결된 CWE 정보와 대응 방법을 가져온다.
- 해당 버전에 패치가 있으면 가져와 적용한다. 보안 사고 대부분은 업데이트와 패치로 예방할 수 있다.
- 사고가 난 뒤 대응하는 것보다 **예방하는 워크플로를 시스템으로 만드는 것**이 중요하다.
- CVE, CWE 개념은 이후 실습에서도 계속 반복된다고 언급.

### 10:04~10:20 Anthropic의 에이전트 정의와 디자인 패턴
- Anthropic은 에이전트 시스템을 **워크플로**(사람이 정해 둔 코드 경로로 LLM과 도구를 조율)와 **에이전트**(LLM이 스스로 과정과 도구 사용을 결정)로 나눈다.
- 실제로 에이전트를 만들 때는 워크플로를 만들고 통제하는 일이 대부분이라, 이 정의가 개발자에게 더 실용적이라고 평가.
- 패턴 소개: 순차 체이닝(결과를 다음 LLM 호출로 넘김), 라우팅(입력을 보고 갈 경로를 결정), 오케스트레이터-워커(작업을 나눠 위임한 뒤 결과를 종합), 평가자-최적화(결과가 마음에 들지 않으면 다시 생성). 각 LLM 호출에는 도구가 붙을 수 있다.
- 실제 시스템은 이 패턴들을 조합한 형태지만 기본 틀에서 크게 벗어나지 않는다.
- **단순한 설계가 최고**: 누구나 이해할 수 있는 워크플로를 만들 것. LLM 호출이 많아질수록 위험과 비용이 커진다. 최신 기술을 과시하는 것보다 단순한 시스템을 잘 만드는 것이 중요하다.

### 10:38~10:58 실습: simple_agent 노트북 (가장 단순한 체이닝)
- 첫 셀은 LLM 호출 결과를 다음 호출로 넘기는 가장 단순한 순차 체인 구조.
- `.env` 파일은 상위 폴더에 두고 `load_dotenv`로 API 키를 읽어 온다. 클라이언트는 OpenAI와 Gemini를 사용.
- 메시지 역할 설명: 시스템 메시지(예: "당신은 보안 전문가이고 CVE에 대해 답변한다")와 사용자 메시지로 구성하고, `chat.completions.create`에 모델(mini 계열)과 메시지를 넘긴다.
- 1단계에서 CVE ID를 묻고, 2단계에서 CWE 전문가 역할로 그 CWE의 대응 방법을 묻는다(f-string으로 앞 결과를 전달). 모델을 바꿔서도 실행해 보도록 함.
- 같은 질문을 다시 실행하면 CVE/CWE ID와 답변이 **매번 달라지고 틀리는 경우도 있음**을 직접 확인함.
- 이렇게 나온 답을 그대로 다음 단계에 쓰는 에이전트는 실제 보안 업무에서는 "망하는 길"이라고 경고.

### 10:58~11:05 정확도 측정과 비교 실습
- 실제 데이터(NVD 등)와 비교해 보니 일부 CWE ID는 맞고 일부는 틀림. LLM 답변은 초안으로만 보고 그대로 믿지 말 것.
- "대한민국의 수도"처럼 단순한 질문은 괜찮지만, 복잡한 질문은 환각 위험이 크다.
- 정확도를 측정하고 검증하는 장치를 시스템 안에 넣어야 한다(평가의 필요성).
- 이전에 만든 RAG 스크립트들과 결과를 비교해 보는 실습을 지시(구체적인 스크립트 이름은 인식 불분명).

### 교수님이 강조한 것
- 매일 도는 일은 에이전트가 아니라 **코드**가 하게 할 것. AI는 코드를 만들 때 쓴다.
- 자기가 만든 코드는 전부 이해하고 설명할 수 있어야 한다.
- **문서화와 기록**이 가장 중요하다. 기록이 있으면 AI로 다시 재현할 수 있다.
- 에이전트끼리 위임할수록 통제가 어려워진다. 설계는 단순하게, LLM 호출은 최소로 할 것.
- LLM 답변은 매번 달라지고 틀릴 수 있으므로 반드시 검증할 것.
- 보안은 사후 대응보다 패치와 업데이트 중심의 예방이 핵심이다.

### 13:11~13:22 에이전트 생태계 정리와 에이전트의 구성 요소
- 오전 내용 정리: 실제 회사에서는 이런 시스템을 로컬 PC보다 클라우드(AWS 등)에 올려서 돌리는 경우가 많습니다. 오늘 실습도 나중에 클라우드에서 비슷하게 진행된다고 보면 됩니다.
- 에이전트 프레임워크·플랫폼을 다시 소개했습니다(CrewAI, Claude Agent SDK, OpenAI Agents SDK, LangGraph, Vertex AI, Microsoft Foundry 등). 회사가 코딩 위주면 LangChain/LangGraph, UI 쪽 시판이 필요하면 OpenAI 쪽이 자주 쓰인다는 설명이었습니다.
- IT 일을 계속할 생각이라면 클라우드 업체의 에이전트 교육을 따로 들어 보라고 권했습니다.
- 에이전트의 구성 요소는 모델(LLM), 역할을 정하는 지시문(instructions), 실제로 실행하는 도구(tool, `@function_tool`), 메모리·상태(단기/장기, stateful), 가드레일(욕설이 들어오면 차단)입니다.
- 동기와 비동기(async) 설명: 비동기 함수는 `await`로 불러야 하고, 실행은 `asyncio.run`으로 합니다. `await`를 빠뜨리면 코루틴 객체만 만들어지고 결과는 나오지 않습니다. 이벤트 루프 안에서 `time.sleep` 같은 블로킹 호출을 쓰면 안 된다는 주의도 있었습니다. 노트북의 설명은 꼭 한 번 읽어 보라고 했습니다.

### 13:22~13:40 OpenAI Agents SDK 기초: Agent, Runner, 날씨 도구, 트레이스
- openai-agents 패키지를 설치(uv)하고, `Agent(name, instructions, tools)`를 만든 뒤 `Runner.run(agent, 입력)`으로 실행하는 기본 형태를 시연했습니다. 처음 만든 에이전트는 도구 없이 지시문만 있었습니다. (13:26 전후에 1~3분 정도 짧게 쉼)
- 고정값만 돌려주는 가짜 날씨 도구는 무엇을 물어봐도 같은 답을 냅니다. 그래서 Open-Meteo API로 실제 날씨를 가져오는 `get_current_weather` 도구로 바꿨습니다(서울·부산·대구 기온 조회 시연).
- API는 요청 파라미터 규칙대로 호출하면 된다고 했습니다(전날 수집 실습과 같은 방식). 무료든 유료든 데이터를 주는 사이트는 많으니 잘 찾아서 활용하라고 했습니다.
- 도구 설명(docstring)에 "도시명은 영어로 변환해서 넣을 것"이라고 적어 두었습니다. 도구의 description은 단순한 주석이 아니라 LLM이 읽는 지시라는 점을 강조했습니다.
- 대단한 튜닝보다 일상의 상식(common sense)을 짧고 명확하게 전달하는 것이 중요하다고 했습니다. 코드는 틀리면 바로 에러가 나지만 LLM은 틀려도 티가 나지 않으니 문장을 더 신경 써서 써야 합니다. 문장이 길고 장황해지면 AI가 헷갈립니다.
- 트레이스: platform.openai.com의 Logs → Traces에서 에이전트가 어떤 도구를 어떤 입력으로 호출했는지 볼 수 있습니다. 문제가 생겼을 때 판단 과정을 추적하는 데 필수라고 했습니다.

### 13:40~14:00 트레이스 확인, 활용 아이디어, 핸드오프, 가드레일, 세션
- (13:40~13:43) 일부 학생은 공유 키로 트레이스가 보이지 않아 확인 방법을 맞췄습니다. Logs 화면에는 전날 파인튜닝 데이터도 함께 올라가 있었습니다. 크레딧 사용량을 계산하고 관리하는 것도 중요하다고 했습니다.
- 활용 아이디어로 음악·글쓰기·검수·편집을 맡는 에이전트 여러 개를 엮어 콘텐츠를 자동 생성하는 사례를 들었습니다. 결과물의 질은 결국 사람의 디테일과 상식에서 나온다고 했고, 저작권 확인이 필요하다는 점도 언급했습니다.
- 핸드오프: 접수 담당(triage)이 결제 담당이나 기술 담당으로 넘기는 구조입니다. 콜센터에서 담당 부서로 돌리는 것과 같지만, 어느 쪽으로 보낼지는 LLM이 정합니다. 모호한 질문이면 어디로 갈지 예측할 수 없으니 핸드오프는 신중하게 써야 한다고 했습니다.
- 입력 가드레일(욕설 차단) 시연: 욕설이 들어오면 tripwire가 걸려 바로 실행이 멈춥니다.
- 세션 메모리: 에이전트는 기본적으로 stateless라서 "내 이름은 민수예요" 다음에 이름을 물으면 기억하지 못합니다. `SQLiteSession`을 `Runner.run`에 넘기면 대화가 기록돼 기억합니다. 이전 대화를 `to_input_list()`로 리스트에 계속 붙여 넣는 방식도 함께 소개했습니다.
- 실습을 돌려 본 뒤 체크하라고 했습니다.

### 16:11~16:25 security_briefing_by_llm: LLM 매니저가 도구 순서를 결정
- 코드 주도 방식에서는 순서가 코드에 고정돼 있습니다. LLM 방식에서는 매니저 에이전트가 도구를 골라 호출 순서를 스스로 정합니다. 업무가 바뀌면 코드 대신 지시문만 고치면 됩니다.
- 앞부분(자산 로드, NVD 조회, 매칭, 위험 평가)은 같습니다. 차이는 각 단계를 `function_tool`로 만들어 매니저 에이전트에 다섯 개 도구로 붙인다는 점입니다(load_assets, search_cves, match, briefing, send).
- 매니저 지시문에도 디테일이 중요하다고 했습니다(예: 한국어로, 단계별로, 어떤 기준으로). 지시를 잘해야 문제를 일으키지 않는 에이전트가 됩니다.
- 공식처럼 정리했습니다: "에이전트 만들고 → `Runner.run`".
- 확장 아이디어: 오전에 만든 RAG 앱(security RAG advance)처럼 이미 만든 시스템도 함수로 감싸면 도구가 됩니다. 에이전트가 다른 에이전트를 도구로 부를 수도 있습니다. 오픈소스 LLM, 사내 RAG, 내부 도구만 쓰면 데이터가 밖으로 나가지 않으니 금융·공공기관 같은 곳에서 이런 방식으로 에이전트를 구축한다고 설명했습니다.
